# Decisions

Choices made where the spec was silent or ambiguous. Newest at the bottom.

## 2026-10-03 · Foundation, tenancy and CRM

- **API framework: Fastify + Zod.** Request and response schemas live in `packages/domain` as Zod objects; the API validates with them and publishes OpenAPI from them (`/openapi.json`, dev only). The web app imports the same types, so there is one source of truth instead of a generated client.
- **Database access: Kysely over `pg`, plain SQL migrations.** Migrations are numbered `.sql` files in `packages/db/migrations`, applied in order by a ~50-line runner that records them in `schema_migrations`. Applied files are never edited. The API applies pending migrations on startup.
- **Tenant isolation is enforced twice.** Every query is scoped by the session's `organization_id`, and child tables reference parents through composite `(organization_id, parent_id)` foreign keys, so the database rejects a row whose parent belongs to another organization. Postgres row-level security was considered and deferred: it needs a separate non-owner database role, which complicates local setup; revisit before production.
- **Other organizations' records return 404, not 403**, so ids cannot be probed across tenants.
- **Auth: email + password, server-side sessions.** Passwords are hashed with scrypt (`node:crypto`, no native modules). The session token is a random 256-bit value in an `httpOnly`, `SameSite=Lax` cookie (Secure in production); only its SHA-256 hash is stored. Sessions last 30 days so technicians stay signed in on their phones; deactivating a user or membership cuts off existing sessions immediately. Magic links / SSO can come later.
- **One session = one organization.** A user in several organizations picks one at sign-in (`organizationId`, defaulting to their oldest membership). An organization switcher can be added when someone needs it.
- **Deny by default is checked at startup.** Every route must declare `config.permission` (or `config.public`), or the app refuses to register it. Role → permission mapping lives only in `packages/domain/src/roles.ts`. Technicians and read-only users can read CRM records but not change them.
- **CSRF:** `SameSite=Lax` plus a rule that every state-changing request must be `application/json`, which a cross-site form cannot send without a CORS preflight.
- **Sign-in rate limit:** 10 attempts per minute per IP + email.
- **Audit log:** `audit_events` is append-only (a trigger rejects UPDATE/DELETE). Every create/update in the API writes one event with the actor, request id and submitted fields. The per-site compliance ledger (`compliance_events`) is a separate table that arrives with the reports module.
- **Sites, not jurisdictions yet.** `sites.jurisdiction_id` is left out until the compliance module adds the `jurisdictions` table, so there is no dangling column. `sites.county` holds the free-text county for now.
- **Equipment table deferred.** Not needed for the core loop; `wastewater_systems` carries manufacturer/model/serial.
- **Object storage deferred to the reports module.** The `minio/minio` image is no longer published on Docker Hub, so the S3-compatible service will be chosen when photos and PDFs need it.
- **Web app talks to the API through a same-origin `/api` rewrite**, so the session cookie is first-party and no CORS is needed. Pages are client components for now; the technician PWA will be offline-first anyway.
- **TypeScript runs directly via `tsx`** in the API and scripts; internal packages export `.ts` source. A compile step can be added when deploy targets are chosen.

## 2026-10-03 · Plans, contracts and service obligations

- **One obligation row per visit.** A contract materializes a `service_obligations` row for each visit in its term (an annual plan with 3 visits makes 3 rows). Each row is the unit the office schedules, a job is assigned to and an inspection completes. This is simpler to schedule and audit than one rolling row per contract.
- **Visit windows split the term evenly.** A 12-month term with 3 visits gives three 4-month windows; each visit is due on the last day of its window, and is overdue the day after. Plans must divide the term into whole months (12/3, 12/4, 24/6…), enforced in the API and by a database check. Shifting later windows after an early or late inspection is a decision for the inspections module.
- **Visit counts and intervals are provider plan settings, not jurisdiction rules.** No county requirement is assumed here; when the compliance engine arrives, a ruleset can require a minimum visit count and the contract form can warn.
- **Contracts copy their plan's terms** (name, term, visits, price, billing frequency) when created, so editing or retiring a plan never rewrites an existing contract. A negotiated price can override the plan price.
- **Contract state is derived, not stored.** The table stores `active` or `cancelled`; `upcoming` and `expired` come from the start/end dates and the organization's own "today" (its timezone, default America/Chicago). No nightly job has to flip statuses.
- **No overlapping contracts per site.** A Postgres exclusion constraint rejects two non-cancelled contracts on one site whose dates overlap; the API answers 409.
- **Renewal, minimal version.** "Renew" creates the next term starting the day after the old one ends, linked by `previous_contract_id`, with the same terms unless a plan or price is given. The old contract and its visits are untouched. A contract can be renewed once. Campaigns, e-signature and payment stay out of scope; `renewal_status` is the seam for them.
- **Cancelling** keeps the contract with its reason and time, cancels its open visits and keeps completed ones as history.
- **The due-inspections list** shows open visits due on or before a date (default today + 30 days), overdue first. It becomes the left column of the scheduling screen in the next module.

## 2026-10-04 · Jobs and scheduling

- **A job is a visit put on a technician's day.** It has a date and a stop order, not a clock time; providers plan by day and route. A clock-time window can be added if customers need appointments.
- **Unscheduled work is derived:** an open visit with no live job. Cancelling (unscheduling) a job puts its visit back in the list. A partial unique index allows at most one live job per visit.
- **Versioned job state machine** (`packages/domain/src/jobs.ts`): scheduled → in progress → completed, with cancel from scheduled or in progress. Each job stores the version it was created under. This module only uses scheduled and cancelled; the inspection module drives the rest.
- **Who can be assigned:** active members with the technician or owner role, because small providers often have the owner inspecting too. Office and read-only members cannot be put on a route.
- **Stop order is manual** (move up/down, or `POST /schedule/reorder` with the full list). A moved job goes to the end of its new day. Route optimization stays out of scope.
- **The technician route** (`GET /route`) returns only the signed-in user's stops for a day, with what the stop card needs: address and coordinates, gate code, access and scheduling notes, safety flags, permit, customer phone and the system on site. The technician app in the next module reads this.

## 2026-10-04 · Inspections, photos and templates (API)

- **Templates are data with immutable versions.** The built-in "Aerobic maintenance inspection" covers the canonical fields in PRODUCT-SPEC §5.7 and is stored on first use from `packages/domain/src/inspections.ts`. An owner customizes it by saving a new version for their organization; a database trigger rejects edits to a saved version. New inspections use the newest version; each inspection keeps the version it started with.
- **Required and optional choices in the built-in template are a provider default, not a county rule.** The compliance module will add jurisdiction requirements on top. Chlorine level is required only when a chlorinator is present; an aerator marked "fail" requires a photo of the problem.
- **One validation function, shared.** `validateInspection` runs in the phone app before completing and in the API when the completion arrives, so they cannot disagree. A completion that fails validation (for example, photos not uploaded yet) is stored as a draft marked `invalid` with the list of problems, not rejected with an error, so nothing the technician entered is lost.
- **The phone creates the ids.** Inspections, photos and issues carry a client-generated UUID, unique per organization. The phone sends the whole inspection after every change and on every retry (`PUT /inspections/sync`); the same id always means the same record, which is what makes offline replay exactly-once. Photos upload one at a time to `PUT /inspections/:clientId/photos/:photoClientId` as the raw image body, with metadata in headers; a retry returns the stored photo.
- **Completed is final.** Once an inspection is completed, later syncs (a retried completion, or a stale draft arriving late) get the completed record back unchanged, and photos can no longer be added. Corrections after completion are a later feature (an amendment with its own audit trail), so filed reports stay trustworthy. `locked_at` is the seam for locking at filing.
- **Answers to hidden fields are dropped on completion,** for example a chlorine level entered before switching the chlorinator to "not present", so reports never show answers the final form did not ask for.
- **Only the assigned technician records the inspection.** Completing it completes the job and its visit. Office and owner users with `inspections:review` can accept an inspection that failed validation, with a written reason; the override and the problems it overrode go in the audit log.
- **Photos are stored behind an `ObjectStore` interface.** Local disk is the only implementation for now (a Docker volume in Compose); an S3-compatible store can be added behind the same interface for production. Files are never public: the API hands out links that expire after 15 minutes, signed with an HMAC over the organization id, file id and expiry, so a link opens exactly one file in one tenant. `FILE_SIGNING_SECRET` is required in production.
- **Photo uploads are the one exception to the JSON-only rule.** Routes that opt in accept `image/jpeg`, `png`, `webp`, `heic` or `heif` up to 15 MB. `image/*` is not a CORS-safelisted type and the route uses PUT, so a cross-site form still cannot reach it.
- **Issues found on a visit** (repair needed, pump-out, part replacement, callback, estimate, noncompliance) are recorded with the inspection and stay open for the exception inbox to pick up.

## 2026-10-04 · Technician phone app (offline)

- **A web app installed to the home screen, not a native app.** `/tech` is a Progressive Web App: one page with its own phone-first screens (today's route, stop card, inspection form). Technicians land there after signing in. Native apps can come later if the camera or background sync need them.
- **The app itself works offline through a service worker** (`apps/web/public/sw.js`). It keeps the `/tech` page and its scripts cached, loads the page from the network when there is signal and from the cache when there is not. It never handles `/api` requests, so it cannot serve stale data or swallow a write.
- **Data lives in IndexedDB on the phone:** the day's route, the template versions, inspections in progress, photos not yet sent, and an outbox. The route is saved whenever the app opens with signal; a technician should open the app once in the morning.
- **Every change goes through the outbox.** Saving an inspection and queueing its sync happen in one IndexedDB transaction, so a change is never saved without being queued. The outbox is sent oldest first, one item at a time and one browser tab at a time (Web Locks). A sync always sends the newest saved state, so queued edits collapse into one request. Completion is held back until that inspection's photos are uploaded, so the server's validation sees them.
- **Retries are safe because the server is idempotent** (see the inspections API decisions). No signal, a timeout, a server error or an expired session leaves the item queued and retries when the phone comes back online, every 20 seconds while anything is waiting, or when the technician taps "Try now". A request the server refuses (for example, the office unscheduled the job) is set aside and shown as needing attention instead of blocking everything behind it.
- **Photos are shrunk on the phone** to at most 2000 px JPEG before queueing, and deleted from the phone once uploaded.
- **Signing out with unsent changes asks first.** The changes stay on the phone either way.
- **Tested end to end:** `apps/web/e2e/offline-sync.spec.ts` signs in, goes offline, does two inspections with photos, reloads the app offline, comes back online, drops the first response to the completing request (the server records it but the phone never hears back), and checks the server ends up with exactly two inspections, four photos and two completions. It runs in CI against a fresh seeded database.

## 2026-10-04 · Reports, compliance history and the background worker

- **A small task queue in Postgres** (`background_tasks`, `packages/tasks`) instead of Redis or a hosted queue: one less service to run. Tasks are queued in the same transaction as the change that needs them, claimed with `FOR UPDATE SKIP LOCKED` so several workers can run, retried with exponential backoff (15 s doubling, capped at an hour, 8 attempts), and reclaimed if a worker dies holding one for more than 10 minutes. A `dedupe_key` makes queueing idempotent. `apps/worker` is the process that runs them; tests run the same code inline.
- **Reports are made by the worker, not in the request,** so a slow PDF or a storage hiccup never fails the technician's sync. Completing an inspection (or the office accepting one) queues `reports.generate`; the office sees "pending" until both copies exist.
- **Two copies per inspection: customer and authority.** The customer copy has every answer, the photos, every finding and the customer notes. The authority copy is the form itself: the check results and readings, the technician's license and the completion location, and only noncompliance findings; no photos and no customer notes. Template fields can say which copies show them (`audiences`). This is a provider default; the compliance module can let a jurisdiction's ruleset ask for more.
- **Reports never change.** Each report stores the exact data it was drawn from (`snapshot`) beside the PDF and its SHA-256, so a later template change or an edited customer or site never alters it. A database trigger rejects updates and deletes. Making reports again for the same inspection is a no-op; a corrected report would be a new version (the `version` column), which is not built yet.
- **PDFs are drawn with PDFKit** (pure JavaScript, no headless browser to run on the server). Only JPEG and PNG photos can be embedded; other formats are listed as "photo on file".
- **Report links are signed like photo links**, with the kind of file in the signature, so a photo link cannot be turned into a report link or the reverse.
- **The compliance ledger** (`compliance_events`) is append-only and written for people: "Inspection completed", "Customer report generated", and later each filing step. The site page shows it as a timeline with links to the PDFs. It is separate from the audit log, which records every change for troubleshooting.
- **Storage moved to `packages/storage`** so the API and the worker share it. Local disk is still the only implementation, shared between the two through a Docker volume.

## 2026-10-04 · Compliance engine and filing

- **Rulesets are JSON files shipped with the code** (`packages/compliance/rulesets/<jurisdiction>/v<n>.json`), validated by a Zod schema and copied into `jurisdiction_rulesets` when the API or worker starts. A published version can never change: a database trigger rejects edits, and startup fails if a file no longer matches what was published. Rules change by adding the next version with its own effective date.
- **Jurisdictions are shared, not per organization.** A county's rules are the same for every provider. Sites are per organization and point at them.
- **Resolving a site's authority:** an authority chosen by hand on the site wins; otherwise the site's county is matched (case-insensitively, "County" optional) against the counties each ruleset covers, in the site's state. No match, or more than one, resolves to nothing; the filing then needs review instead of going to a guessed authority. The ruleset in force on the inspection date is used, and the filing records exactly which one.
- **Only a fictional authority exists.** `tx-example-county` covers sites in "Example County"; the seed puts half the demo sites there and half in "Sample County", which has no authority, so both paths are visible. Its rules (air pressure required, technician license required, file within 14 days, warn 5 days before, inspect every 4 months) are invented for testing.
- **A jurisdiction's requirements sit on top of the template.** Fields it lists become required and photo minimums rise, but conditional fields stay conditional. The technician's route carries the requirements for each stop, so the phone enforces them offline with the same validation function the API uses. An override by the office can still accept an inspection without them; its filing then stops in needs review.
- **One filing per completed inspection,** opened in the same transaction that completes it. It waits (`pending`) until the reports worker has made the authority copy, then is checked against the ruleset and becomes `ready` or `needs_review`. Ready email filings are queued straight away when the ruleset says `autoSubmit`.
- **State machine (version 1):** pending → ready → queued → submitting → sent → confirmed, with failed (retryable), rejected (resubmittable) and needs_review (re-checkable). `sent` needs proof (the email Message-ID, or what the office recorded when filing by hand); `confirmed` needs the authority's reference. Database checks enforce both, so sent can never be mistaken for confirmed. The filing deadline counts as met once sent.
- **Retries never send twice.** Each submission has one idempotency key (`filing-<id>-submission-<n>`), reused by every retry and used as the Message-ID. The mail transport must deliver a key at most once and answer repeats with the first result; the development outbox does. So a retry after a lost response, a duplicate task, or a worker crash mid-send cannot produce a second email. Only a deliberate resubmission after a rejection gets a new key.
- **Failures:** each failed try is recorded as a filing attempt; the queue retries with its usual backoff (8 tries). Only the first failure of a submission goes on the compliance timeline, so automatic retries do not flood it. The office can retry at once (which pulls the waiting retry forward rather than queueing a second one) or switch to filing by hand.
- **Filing by hand** is the fallback the ruleset names (`manual_export`): the office downloads the authority report, files it on the portal or by mail, and records the portal reference. The pending automatic retry then finds the filing handled and does nothing.
- **Next due date** is the inspection date plus the authority's interval, stored on the filing and shown with it. It is not yet compared with the contract's next visit; the exception inbox will flag a visit scheduled later than the authority allows.
- **Permissions:** `filings:read` for owner, office and read-only; `filings:write` (acting on filings) for owner and office. Technicians do not see filings.

## 2026-10-04 · Exception inbox

- **The inbox is the office's home screen** (`/` goes to `/inbox`; technicians are sent on to `/tech`). It shows four counts (due this week, overdue, filings at risk, contracts expiring), the exceptions list, and today's routes. Unpaid balances wait for invoicing; renewal pipeline and recent activity wait for their modules.
- **Exceptions are computed, not stored.** Each request derives them from the records: an open visit past due, an inspection whose completion failed validation, a filing that failed, was rejected, needs review, is near or past its deadline, or was sent 14+ days ago without confirmation, a site whose next visit cannot meet the authority's next due date, an open issue on a finished inspection, and a contract ending within 30 days (or ended in the last 60) with no renewal or later contract. An exception disappears the moment its cause is fixed, so the inbox can never disagree with the data. The `exceptions` table in DOMAIN-MODEL is deferred until something needs to be stored on one (snoozing, assigning, comments).
- **Each kind is capped at 200 rows** so one flood cannot hide everything else. Order: high, medium, low severity, then earliest date.
- **"Next visit later than the authority allows"** only fires when it cannot be fixed by scheduling within the window: there is no open visit, the visit's window opens after the authority's date, or the date is within 30 days and the visit is not on a route by then. Comparing due dates alone flagged nearly every site, because a visit's due date is the end of its window.
- **Two exceptions are handled in place:** accepting an unfinished inspection (the existing supervisor override, reason required) and resolving an issue (a written resolution, kept on the issue with who and when). Everything else links to the screen that fixes it.
- **Access:** the inbox needs `filings:read` (owner, office, read-only). Resolving an issue needs `inspections:review` (owner, office).

## 2026-10-04 · Customer import

- **One row is one service site.** Rows can carry the customer, their phone and email, the site address, county, permit, gate code and notes, the unit's make, model and serial, and a plan with a contract start. Rows with the same customer name and the same phone or email become one customer with several sites; a row matching a customer already on file by name and phone or email adds a site to that customer.
- **The file goes up as base64 inside JSON** (`POST /imports`), so the upload keeps the JSON-only rule that protects against cross-site form posts. Files are capped at 10 MB and 5,000 rows. CSV (comma, semicolon or tab, with or without a BOM) is read with csv-parse; `.xlsx` with exceljs, taking the first sheet that has rows and turning Excel dates into ISO dates. Old `.xls` files are refused with a message to save as `.xlsx` or CSV.
- **Columns are detected from headers, then values.** Each field has a list of header names ("Client Name", "Svc Address", "Permit #", "S/N"...); an exact match wins, then a header containing one. Unlabeled columns that look like emails, phone numbers or ZIP codes are recognized by their values. The office can change the mapping on the preview.
- **The preview is recomputed, not stored.** The raw cells of every row are kept (`import_rows.raw`); what each row becomes, its problems and its duplicates are derived on each read, so changing the mapping, adding a plan or adding a customer elsewhere is reflected at once. Only the office's include or skip choice is stored per row.
- **Row statuses:** `error` (no customer name, address or city; never imported), `duplicate` (same address, typed any way, or same permit as an earlier row or a site already on file; skipped unless ticked), `warning` (imported, with values left out: a phone that is not 10 US digits, a bad email, an unknown state, ZIP or date, an unknown plan, or a name shared with an existing customer without a shared phone or email), `ready`.
- **Commit is all or nothing.** Every included row is saved in one transaction: customers, a primary contact, sites, systems, and contracts with their visits through the same code the contracts screen uses. If anything fails, nothing is kept, the import is marked failed with the reason, and it can be committed again once the cause is fixed. Imported customers and sites carry `import_id`, and each row records what it created.
- **Contracts from an import are not set to renew automatically**, the same default as the contracts screen.
- **Auditing:** one audit event per import step (created, mapping changed, rows changed, committed with counts, failed, discarded) rather than one per created record; the records point back to the import through `import_id`.
- **Access:** importing needs `crm:write` (owner and office).

## 2026-10-04 · Invoicing and payments

- **Invoice status and payment status are separate,** as the Stripe notes ask. An invoice is a `draft` (editable, unnumbered), `open` (issued) or `void`. Its payment status is `unpaid`, `processing` (a bank payment is clearing), `partial`, `paid`, `overpaid` or `refunded`, recomputed from its payments and refunds in the same transaction as every change to them (`recalcInvoice` in `packages/payments`). Money on a void invoice counts as overpaid, so it shows up to be refunded.
- **Issued invoices never change.** Issuing assigns the next number (per organization, from 1001, shown as `INV-1001`; drafts have none, so there are no gaps), fixes the issue and due dates in the organization's timezone, and freezes what the invoice says into a snapshot. The PDF and the customer's pay page are drawn from the snapshot, so editing the customer later never changes an invoice already sent. Database triggers refuse edits to an issued invoice or its lines, a second PDF, un-voiding, and deleting anything but a draft. Corrections are void and reissue; there are no credit notes.
- **Totals:** integer cents; quantities are whole numbers. The discount comes off the subtotal before tax and is spread over taxable and untaxed lines in proportion. Tax is one rate per invoice (basis points; the organization's default, 0% unless set) charged on lines marked taxable, rounded once on the invoice. Whether septic maintenance is taxable in Texas depends on the work and the property, so lines default to untaxed and the office decides.
- **Contracts are billed in installments** that follow the billing frequency (annual: one; quarterly: four, and so on). Amounts follow the months each period covers, with the rounding remainder on the first installment. "Bill next installment" makes a draft for the earliest installment not on an invoice that is not void, locking the contract row so two people cannot bill the same installment. Billing is a button, not automatic; renewals will collect payment for the next term.
- **The customer's pay link is a random token** on the invoice (like a signed link, but it stops working when the invoice is voided). The page shows only what the snapshot says plus what is still due. It needs no sign-in, and the routes are rate-limited.
- **Stripe Connect with direct charges.** Each provider connects their own Stripe account (Express); customers pay on that account through Stripe Checkout and the money settles to the provider. Aerowise takes no application fee for now. Which methods appear (card, US bank account, wallets) follows the account's payment method settings. Checkout charges what is still due; an open page for the same amount is reused, so pressing Pay twice does not make two payable pages, and voiding an invoice expires its open pages.
- **Webhooks are verified, idempotent and replay safe.** The signature is checked on the exact bytes received (the route keeps the raw body). Each event id is recorded in `stripe_events` in the same transaction that applies it, so a replay is skipped and a failure leaves nothing behind. Events are matched to an organization by the connected account they came from, never by metadata alone. Payments are keyed by Stripe's PaymentIntent and move only forward (pending → succeeded or failed), so out-of-order events settle to the same result. Refunds are keyed by Stripe's refund id; refunds made in the Stripe dashboard are picked up too.
- **Bank payments (ACH)** complete checkout unpaid and clear days later: the invoice shows `processing` and is not offered for payment again meanwhile. A failed bank payment goes back to owed, the customer can pay again from the same link, and it shows in the inbox as high severity.
- **Payments recorded by hand** (check, cash, other) cannot exceed what is still due. Refunds of those are recorded after the money has been handed back; refunds of card and bank payments go through Stripe with an idempotency key per refund request.
- **Permissions:** `invoices:read` (owner, office, read-only), `invoices:write` (owner, office: drafts, issuing, sending, voiding, recording payments) and `billing:manage` (owner: Stripe, invoice defaults, refunds). Technicians see no invoices.
- **Inbox:** unpaid invoice count and amount as a tile; exceptions for an overdue invoice (low, medium after 30 days), a failed bank payment in the last 30 days still owed (high), and an overpaid or paid-while-void invoice (medium). Exceptions about an invoice with no site show the customer instead.
- **Development without Stripe:** a built-in test provider (`TestPaymentProvider`) runs whenever no `STRIPE_SECRET_KEY` is set outside production. Connecting is instant, checkout opens `/pay/<token>/test-checkout`, and its buttons (card, bank clears, bank still clearing, bank fails, declined) play the webhooks Stripe would send, signed with Stripe's own scheme and delivered through the real webhook route. In production without keys, online payment is simply off.
- **Emails:** issuing with "email" queues the PDF and the email in the issuing transaction; the worker renders the PDF once and sends with a per-send idempotency key, so a retried task never emails twice. Invoices go to the customer's billing contact, else the primary contact, else any contact with an email; transactional email does not need marketing consent.
- **Payments on the compliance timeline:** a cleared payment on an invoice for a site adds "Payment received" to that site's history, as the spec's timeline lists.

## 2026-10-04 · QuickBooks Online sync

- **One way, Aerowise to QuickBooks.** Customers, invoices and payments are sent; nothing in QuickBooks is changed or deleted without a person choosing to. Edits made in QuickBooks are read (change data capture) only to notice conflicts, never copied into Aerowise. Two-way customer updates, tax, refunds and estimates are later, as the spec lists.
- **Customers become QuickBooks customers; sites are not sub-customers yet.** The site's address goes on the QuickBooks invoice as its shipping address. Most providers keep one QuickBooks customer per homeowner, and sub-customers can be added when someone needs them.
- **Plans are the products.** There is no product catalog, so each plan maps to a QuickBooks item (its installments use it) and one item covers every other line ("other charges"). Several plans may share an item. A missing, deleted or inactive item stops the invoice as a conflict until the mapping is fixed; saving the mapping puts those invoices back in line.
- **First sync is a review, not an import.** Connecting reads every active QuickBooks customer and proposes one choice per Aerowise customer. Only an exact match is linked without asking: exactly one QuickBooks customer with the same name (case, punctuation and "Last, First" ignored) and the same email or phone (last ten digits). A same name alone, a similar name (letter-pair similarity of 0.8 or more), a shared email or phone under another name, or two exact matches go to a person. Customers with no likely match are created. A person can link, create or skip each one; undecided customers go to the conflict center at commit. Matched customers are linked as they are, so QuickBooks keeps its details until the customer next changes in Aerowise.
- **After the first sync, customers are sent when they first need to be:** when their first invoice is sent, matched the same way (asking when unsure). Customers who never get an invoice are not added to QuickBooks.
- **Invoices issued before the sync start date are not sent** (default: the day QuickBooks was connected; the owner can change it), so invoices already entered by hand are not doubled. Before creating an invoice, QuickBooks is searched for its number: the same customer and total is linked, anything else is a "number already used" conflict. Creates carry a request id, so a retry after a timeout cannot make a second copy.
- **Invoices with sales tax are not sent.** QuickBooks US calculates tax itself, so sending tax would make the totals disagree. They wait in the conflict center, to be entered by hand and set aside, until tax mapping is built.
- **Payments:** cleared payments are sent and applied to their invoice. If QuickBooks shows less owed than the payment, it may already be recorded there, so it waits for a person. Refunds are not sent yet.
- **Statuses** follow the spec (new, queued, syncing, synced, conflict, failed, ignored; "not connected" is the absence of a connection). Temporary failures (network, throttling, QuickBooks errors 5xx) retry after 1, 5, 30, 120 and 360 minutes; anything QuickBooks refuses, and anything past the last retry, waits for a person. Records waiting on another record (an invoice on its customer) stay queued and are not counted as problems.
- **Conflict center** is the QuickBooks page: possible matches, changed in both places, deleted or made inactive in QuickBooks, item missing, tax not mapped, payment mismatch, invoice number already used, and failures. Each says what happened and offers the choices that settle it, recommended first. They also show in the inbox.
- **Syncing** runs in the worker: soon after an invoice is issued or voided, a payment clears, a mapping changes or a conflict is decided, and every five minutes regardless. One run at a time per company.
- **Connection:** OAuth 2.0 with Intuit. The `state` is signed and names the person who started connecting; the callback only accepts it from them. Tokens are stored encrypted (AES-256-GCM, `QUICKBOOKS_TOKEN_KEY`), refreshed under a row lock because QuickBooks rotates refresh tokens, and revoked on disconnect. A refused refresh marks the connection "needs reconnecting" and nothing is lost: changes wait. Reconnecting the same company keeps every link; connecting a different company starts over.
- **Access:** connecting, disconnecting and the item mapping need `billing:manage` (owner). Reviewing matches, deciding conflicts and "Sync now" need `quickbooks:write` (owner, office). `quickbooks:read` for owner, office and read-only.
- **Development without Intuit keys:** a built-in test company (`TestQuickBooksProvider`) stands in outside production. Connecting is instant and lands on a company kept in the database (so the API and worker share it), pre-filled with near-copies of the first few customers: one exact, one "Last, First" with the same phone, one twice (ambiguous) and one misspelled, plus two strangers and four items. Tests use `TestCompanies` to play edits, deletions, inactive items and outages in QuickBooks.

## 2026-10-04 · Renewals and e-signature

- **E-signature is built in, not a provider.** The spec asks for a typed or drawn signature, timestamp, IP and device, a signed PDF, an immutable copy and an audit trail; all of that is ours to keep anyway, so no DocuSign-style service (and no credentials) is needed. Signing freezes the agreement exactly as shown into `signed_documents` with the SHA-256 of its canonical JSON. A trigger refuses any change or delete except attaching the PDF once. The worker draws the PDF (agreement, signature, signing certificate) and emails the customer their copy.
- **IP address** is recorded as the request's `X-Forwarded-For` chain plus the address that reached the API, because the API sits behind the web app's proxy. It is evidence, not identity.
- **One renewal at a time per contract.** A declined or expired one can be started again by the office; the campaign never restarts it on its own.
- **The offer** is the contract's plan at its current price when that plan is still offered, otherwise the contract's own terms, starting the day after the contract ends. The office can change plan or price until the customer signs; each change bumps a version, and a customer who opened the older version is asked to review it again before signing.
- **What the customer pays when they renew** is the new term's first installment (the whole price for annual billing) plus each chosen add-on once. Later installments are billed as usual; the renewal invoice's first line is linked to the new contract's first installment when it activates, so that installment is never billed twice. This is the only change ever made to an issued invoice's lines, and the database allows nothing else.
- **When the next term starts** is an organization setting: once the renewal invoice is paid (default), or at signing with the invoice paid on its usual terms. A $0 renewal activates at signing.
- **Activation that needs a person goes to review**, not to an error: the contract was cancelled, renewed by hand, or another contract now covers the dates. It shows in the inbox.
- **Automatic emails are off until the office turns them on**, so connecting a book of contracts never emails everyone at once. The campaign still creates renewals for contracts inside the window (default 60 days) every hour, and reminds at 30 and 7 days before the contract ends (at least 3 days after the last email). Unsigned offers expire when the contract ends.
- **Auto-renew contracts** are renewed by the office with "Auto-renew now", without a new signature (the original agreement allowed it); their first installment is billed the usual way. Doing this automatically on the end date is left for when a provider asks for it.
- **Add-ons** are a small per-organization catalog, offered on every renewal and copied into the renewal when chosen. Contact details the customer confirms update their billing (else primary) contact, with the before and after kept on the renewal.
- **Contracts' `renewal_status` column is no longer read**; the API reports the latest renewal's status instead (`not_started` when there is none).

## 2026-10-04 · Customer portal

- **A magic link, no accounts.** Homeowners never get a password. The office copies or emails a link from the customer's page, or the homeowner types their email at `/portal` and gets one. A link opens one customer's account (every one of their properties) for 90 days.
- **Only a hash of the link is kept.** Unlike pay and renewal links (which show one invoice or one offer), a portal link opens everything about a customer for weeks, so the database stores the SHA-256 of its token and the token exists only in the link. A copied link is shown once. Emailed links are made by the worker when it sends the email, so no token is ever written to the task queue either.
- **Asking by email never says whether the address is on file.** The answer is always the same. Every contact with that email (any provider using Aerowise) gets a link to their own account, at most one email per customer and address every 10 minutes, and five requests per minute per IP address.
- **The office can turn off every link a customer has** at once (a lost phone, a sold house). It also sees how many links work and when one was last opened.
- **What the portal shows:** each active property with its system, the contract in force (else the next, else the last) and visits done, the next visit (its window, or the date it is scheduled), the customer copy of every inspection report (latest version), the renewal (with a link to the renewal page while it can be signed or paid), invoices still owed and the last year of the rest (each through its pay link), and the customer's service requests. Authority copies of reports and anything about other customers are never reachable: report files are served through the link itself and checked against its customer, rather than through the 15-minute signed file links the office uses.
- **Service requests** (alarm, odor or wet area, repair, pumping, a question, other) go to the office inbox until someone closes them with a note, which the homeowner then sees. Alarms and odors are high severity. They are not compliance events. Turning a request into a scheduled visit is left to the office.
- **Saved payment methods are not offered** because there are none yet: each invoice is paid through its own pay link.

## 2026-10-04 · Text messages

- **Twilio, behind an interface, with a built-in stand-in.** There are no provider credentials yet, so outside production a test provider (`TestSmsProvider`) records each text as delivered without sending it, answers Twilio's magic test numbers the way Twilio does, and signs webhooks exactly as Twilio signs them. In production texting is off until `TWILIO_ACCOUNT_SID` and `TWILIO_AUTH_TOKEN` are set. Each organization texts from its own number, which the owner enters; replies find their organization by the number they were sent to.
- **Off until the owner turns it on.** Then four kinds go automatically: on the way, report ready, renewal reminder and payment reminder. "Inspection completed" is available but off by default, because the report-ready text follows within minutes and says more. Only the owner changes these settings.
- **Who gets a text:** one contact per text, the property's own contact first, then primary, billing and any other, among contacts with a usable mobile number who agreed to texts (the existing `consent_sms` box) and whose number has not opted out. When nobody qualifies, nothing is sent and the Texts page says why (no mobile number, no consent, replied STOP), once per text.
- **STOP is final until the customer texts START.** STOP (and the other carrier keywords) records the number as opted out and unticks texting on every contact with that number; the office cannot tick it again while the number is opted out. START, YES or UNSTOP opts the number back in and ticks texting on its contacts, since texting START is the customer agreeing. A carrier "unsubscribed" error does the same as STOP. Twilio answers STOP, START and HELP itself, so Aerowise sends no reply.
- **Quiet hours:** automatic texts go between 8 am and 9 pm in the organization's time zone; one due outside that waits for 8 am. "On the way" is exempt (a technician sends it about a visit happening now), and so is a reminder the office sends by hand.
- **What each text says:** every text starts with the provider's name and ends with "Reply STOP to opt out." On the way names the technician's first name and the street address. Report ready carries a new portal link (made when the text is sent, like emailed links), so the customer opens their report in their account; the stored copy of the text leaves the link out because only a hash of portal links is kept. Renewal reminders carry the renewal link and go with the 30- and 7-day reminder emails, not with the first offer. Payment reminders carry the pay link.
- **Payment reminders** go 3 and 14 days after the due date while something is owed. A reminder missed by more than a week (texting was off) is not sent late, so turning texting on never texts every overdue customer at once. The office can also text a reminder from the invoice, at most once a day per invoice, whether or not automatic payment reminders are on.
- **Each text is sent once.** A text has a key (for example the visit's on-the-way text); a retried task, or a technician tapping "On my way" twice, finds the earlier one. Temporary provider errors retry up to five times; refusals (a landline, an invalid number) fail at once and show on the Texts page. Delivery receipts mark texts delivered or failed.
- **Replies** that are not keywords go to the office inbox ("Customer texted back") until someone marks them handled. A reply from a number no contact has is kept on the Texts page but not put in the inbox, which lists items by customer.
- **Not yet:** two-way conversations from the Texts page (the office answers by phone or its own texting), MMS, per-customer text history on the customer page, A2P 10DLC registration help, and texts in languages other than English.

## 2026-10-04 · Route optimization

- **No paid map service.** Driving is estimated from straight-line distance stretched by 30% for roads, at the organization's average speed (35 mph by default). That is good enough to compare one stop order with another and to say whether a day fits, needs no account or key, and works the same in tests. Real road times (a routing API) can replace the estimate behind the same functions when a provider needs them.
- **Sites are found on the map in the background.** A new site, a changed address, or an import queues a lookup; the worker also sweeps every 15 minutes for anything missed. In production the default geocoder is the US Census Bureau's (free, no key, US addresses only); `GEOCODER=off` turns lookups off. Outside production a built-in test geocoder (`TestGeocoder`) puts each address at a made-up, repeatable spot near central Texas, clustered by city; ZIP 00000 is "not found".
- **Typed coordinates win.** Coordinates entered on a site (or given by the API) are marked as placed by hand and kept when the address is corrected. Coordinates the geocoder found are dropped and found again when the address changes. An address that cannot be found is marked and not retried until it changes or someone asks ("Look up sites again" on Route settings); the site page says what to do.
- **Where routes start** is an organization setting: an address looked up once (or typed coordinates), and whether routes end back there. Without it, a route starts at its first stop. Per-technician start points (a technician who drives home in the company truck) are left for later.
- **Optimizing is a suggestion first.** "Optimize route" shows how much a shorter order saves; "Use this order" puts it in place, re-planned under the same lock a manual reorder takes. Stops already started or done stay first in their order; stops not on the map go last. The current order is kept unless the new one saves at least a quarter mile and 1%, so pressing the button twice never shuffles a route. The search is nearest-neighbour then 2-opt and or-opt, which is close to optimal for a day's 5–25 stops.
- **Capacity** is a working day (8 hours by default) against driving plus an average time per stop (30 minutes by default). A day over it is flagged on the schedule; nothing is blocked. "Nearest to the route" ranks unscheduled visits by the driving they would add to the selected technician's day and flags the ones that would make it run long, which is how the office groups work by geography.
- **The map is drawn, not tiled.** The schedule shows the day's routes to scale on a plain background with numbered stops and a scale bar, so it needs no map tiles, key or third-party script. Street-level detail stays one click away (each site's Map link).
- **Not yet:** technician territories, customer time windows (jobs have no clock time yet), moving stops between technicians automatically, and a multi-day planner.

## 2026-10-04 · Filing readiness for a pilot

- **Authority profiles say how sure they are.** Every non-fictional ruleset carries `profile` (`draft` or `verified`, the sources read and the date, open questions). A verified profile may not have open questions. A draft never queues itself: filings stop at Ready and the office sends them. Fictional rulesets are not loaded in production. Rulesets stay immutable (hash checked); new schema fields are optional so the example ruleset's hash did not change.
- **No county guessing for partial authorities.** An authority with `assignment: "reviewed"` (LCRA, Harris County) never matches a site by county; sites in its counties go to review with the reason and the candidates. A person chooses the authority and must record the evidence (map lookup, determination, permit record). Assignments are append-only. Two whole-county matches also go to review.
- **Credentials are their own records.** MP license, maintenance technician registration, installer license, other; each with holder, number, expiry and when and where it was checked. One person can hold several. The organization names one MP credential as the responsible provider. Profiles can require it, and can require the inspecting technician to hold an active MP or MT credential on the inspection date. The old free-text technician license stays for the example ruleset.
- **Authority identifiers belong to the site and authority** (for example the LCRA OSSF application number) and are checked for presence and, where published, format.
- **A package per submission, made once.** Before a filing is Ready, Aerowise stores the exact documents (cover sheet, authority report version or signed contract), their SHA-256, the cover sheet fields, recipient, subject and body, plus a manifest hash. Sending, retrying and manual filing all use that package; the database refuses changes. A resubmission makes a new package; the old one stays.
- **Contracts are filings too**, in the same table and state machine, with their own deadline basis. They wait for a signed copy (online signature or an uploaded PDF). A sweep opens contract filings that were missed.
- **Complaints and monitoring notices are classified by a person.** Every service request (portal or logged by the office) since the previous inspection must be reviewed before an inspection filing is released, and each owner complaint or monitoring notice needs a recorded response. The authority copy prints them. If responses change after the report was drawn, a linked report version is drawn once nothing else holds the filing. The authority copy now shows every finding except estimates.
- **Corrections never overwrite.** After a rejection the office records corrected answers and a reason; Aerowise draws a new report version that names the one it replaces, then a new submission. Inspection values are not edited.
- **Delivery is recorded per audience.** Customer emails (inspection report, signed agreement) go in `customer_deliveries` with recipient, document hash and the provider's answer; authority sends are `filing_attempts` tied to a package. "Accepted by the mail provider" is all either proves. Acknowledgment is a separate, manual record with evidence.
- **Not done:** reading authority replies, uploading receipts, the six-month electronic-monitoring schedule, a real mail provider, boundary data, and a Brazoria profile.

## 2026-10-04 · Filing readiness: review changes

- **Complaints are asked about per reporting period.** A filing waits only for requests received in its own period (since the previous completed inspection, or from the day before the contract in force started for a site's first report) to be classified. Older requests and requests after the inspection are not asked about. Marking one not reportable releases the filing.
- **An unanswered or unfinished complaint never holds a filing.** 30 TAC 285.7 asks the report to "include any responses to owner complaints", not finished repairs. A response is recorded with an outcome (resolved, or still outstanding). The authority report prints each reportable request with its response and status ("outstanding, no response recorded as of …" when there is none), carries unresolved ones from earlier periods onto later reports ("from an earlier period, still open"), and the inbox shows each unresolved one as high severity until it is resolved.
- **A Ready package that goes stale is replaced, not sent.** If complaint responses change after a filing's package is made but before it is sent, the filing gets a new submission with a redrawn report. The old package stays on record, marked never sent.
- **What a draft profile allows.** Allowed: preparing the package, Send now and Retry now by a person, the queue's automatic retries of that same request (same package, same idempotency key), filing by hand, recording rejection, correction and acknowledgment. Not allowed: anything sending on its own. Becoming Ready, rechecks, the contract sweep, complaint and contract-upload refreshes never queue a send, and the send task itself refuses a submission nobody asked for (it goes back to Ready with a `filing_held` event). A new submission (resubmit, correction, stale package) needs a new Send.
- **Two dates, kept apart.** `profile.sourcesCheckedOn` is when someone read the sources. `profile.requirementEffective` is when the authority's requirement took legal effect, with its evidence, or null when unpublished (Harris County). The ruleset's `effectiveFrom` is only when Aerowise starts applying that version.
- **LCRA's own cover sheet.** The provider supplied LCRA's fillable PDF. It is stored in `packages/compliance/forms/`, pinned by SHA-256 in the ruleset, filled field by field (pdf-lib) and flattened. A form whose hash differs, or that lacks a mapped field, fails packaging.
- **Contract deadline.** 30 TAC 285.7(d)(2): 30 days before the initial two-year service policy expires, and at least 30 days before each later contract expires. Aerowise sets a date only when it knows the end of the contract being replaced. The six-month electronic-monitoring schedule stays unavailable until Aerowise records whether a system qualifies.

## 2026-10-04 · 30 TAC 285.7 follow-up: report signature, contract deadlines by kind, notice when a contract ends

- **The MP signs each authority report (285.7(b)(3)).** For every ruleset with a real authority profile, an inspection filing waits until the latest authority report version is signed. Fictional demo rulesets have no profile and skip this. A signature is an immutable `report_signatures` row: who signed, their MP license, the typed name, the statement, when, and the hash of the unsigned report. It also stores a signed copy, which is the same report rendered with a signature block. The report row is never changed, and the package sends the signed copy. Each new report version needs its own signature.
- **Who may sign:** the signed-in person, using their own MP license. The license must be active, unexpired on the signing day, and recorded as checked against TCEQ's search. They type their name as it appears on the license. By default the MP named on the site's contract signs (`contracts.provider_credential_id`, else the organization's responsible MP). Another MP signs only with a described delegation and supervision, which the statement quotes and the signature row keeps (Justin's conservative product decision in the merge review).
- **Customer copies are signed too** (285.7(b)(3), (e)(1)), in the same step. Where a signature is required, an unsigned customer copy is not shown in the portal, not emailed and not announced by text. Required means every inspection except those under a fictional demo ruleset.
- **Unsigned packages never go out.** The send task, the filing sweep, signing and manual filing each check the package. An unsigned unsent package is replaced by the next submission and kept on record.
- **A recorded end is not the end of service.** A future last day keeps the contract active with the visits that can start by then; the daily sweep ends it the day after. Cancelling a visit for any of these reasons cancels its unstarted job, so the route never shows a visit after service ends; jobs cannot be booked past the last day, and kept visits booked too late are flagged in the inbox. If someone else inspected, their MT or MP registration must have been valid on the inspection date, and the statement attests to employment and direct supervision (285.7(b)(1), 285.2). The permission `reports:sign` goes to owners, office staff and technicians, but the license check is what decides.
- **Contract deadlines by kind.** `contracts.filing_basis` holds the kind: initial policy (285.7(c), no date), first contract after the policy and renewal (285.7(d)(2), 30 days before expiry), or replacement (285.7(d)(3)(C), within 30 days after termination). A renewal made in Aerowise is treated as a renewal of the contract it follows. Any other contract has no deadline until a person records its kind, because Aerowise does not guess. Changing the kind updates only a filing that has not been sent.
- **Ending a contract (285.7(d)(3)(A), (B)).** Cancelling now records who ended the contract and the last day of service. The provider's written notice to the authority and the manufacturer, and to the owner when the provider ended it, is due 30 days before service ends. The inbox shows it, and the office records when it was sent and to whom. Aerowise does not send it, because manufacturer addresses are not in Aerowise.
- **Rule text** for (b), (c) and (d) was read from Cornell LII's republished §285.7 through a fetch tool asked for verbatim quotes. The notes in the v1 rulesets keep their earlier wording about a summarizer, because published versions do not change.

## 2026-10-05 · W2.1 Platform admin and /admin

- **Platform admins are their own identity, not a fifth tenant role.** They live in `platform_admins` with their own password, their own sessions (`platform_admin_sessions`, cookie `aw_admin_session`, 12 hours) and their own sign-in at `/admin/login`. A route opts in with `config.platformAdmin`, which only an admin session satisfies; a tenant session, or a tenant token placed in the admin cookie, gets 401. An admin session never satisfies a tenant route either. The same email can be both a company user and an admin, with two separate passwords and sign-ins. Keeping them apart means no tenant role change, membership bug or seed mistake can ever grant access across organizations.
- **Admins come from the CLI.** `pnpm db:create-platform-admin <email> <name>` with the password on stdin (or `PLATFORM_ADMIN_PASSWORD`), minimum 12 characters. The seed adds `admin@example.com` only when `NODE_ENV` is not `production`.
- **A platform audit log.** Admin actions go to `platform_audit_events` (append-only, like `audit_events`), with the organization acted on when there is one. Tenant `audit_events` needs a tenant user as the actor, which an admin is not. Admin sign-in and sign-out are recorded too.
- **Usage on the organization list.** Active contracts are contracts not cancelled whose dates cover today in the organization's own time zone. Users are active users with an active membership. Last activity is the newer of the latest audit event and the latest sign-in; the seed writes neither, so the demo company shows "Never" until someone signs in.
- **Not in W2.1:** the plan state and price override (W4.1), inviting the first owner (W2.2), and read-only impersonation (W2.6).

## 2026-10-05 · Hosting: Render (W1.1)

- **Render, with everything in one `render.yaml`.** Prices and features were read from each host's pricing and docs pages on 2026-10-05 ([Render pricing](https://render.com/pricing), [Render Blueprint spec](https://render.com/docs/blueprint-spec), [Railway pricing](https://docs.railway.com/reference/pricing/plans), [Railway config as code](https://docs.railway.com/reference/config-as-code), [Fly.io pricing](https://docs.fly.io/about/pricing)).
  - **Render:** one Blueprint file describes both environments, their Postgres 16 databases, disks, health checks, generated secrets and a pre-deploy migration step, so the whole setup is code. Managed Postgres includes point-in-time recovery (3 days on the free Hobby workspace, 7 on Pro). Env vars reach the Docker build, which the web app's baked-in API address needs.
  - **Railway:** config as code covers one service's build and deploy settings only; services, databases and environments are set up by hand in the dashboard. Usage pricing ($20 per vCPU-month, $10 per GB-month of memory, $5 a month on Hobby with $5 of usage included) would cost about the same.
  - **Fly.io:** machines are the cheapest ($3.69 a month for 512 MB) and `release_command` runs migrations, but Managed Postgres starts at $38 a month per database, about $76 for two environments, and the alternative is running Postgres ourselves.
- **Monthly cost on Render** (Hobby workspace, $0): staging about $21 (web and API Starter at $7 each, Basic-256mb Postgres at $6, 1 GB of database storage at $0.30, a 1 GB disk at $0.25); production about $36 (Basic-1gb Postgres at $19, 5 GB of database storage and a 5 GB disk). About $57 for both. That is above the brief's $10–40 estimate; production can be applied later, when the first design partner signs, which keeps the start at about $21. Moving to the Pro workspace ($25 a month) adds 7-day recovery and team seats.
- **The API and the worker run in one service until object storage lands.** Photos and PDFs are on a local disk, a Render disk belongs to one service, and the worker writes files the API serves. `scripts/start-api-and-worker.sh` runs both and exits when either stops. The cost of a disk: no zero-downtime deploys (a few seconds of downtime per API deploy) and no second instance. After W3.2 the worker becomes a separate service and the disk goes away.
- **Worker health is a heartbeat file**, touched after every clean pass of the loop and judged stale after 5 minutes, because one pass can include a slow task. Hosts that run a command use `pnpm --filter @aerowise/worker health`; on Render, where only web services get health checks, the shared service's `/health` includes it (`HEALTH_INCLUDES_WORKER=true`). The default `/health` is unchanged.
- **Deploys are explicit.** `autoDeployTrigger` is off for every service; `scripts/deploy.sh` deploys the API (migrations first, in Render's pre-deploy step) and waits for it before the web app. CI calls the same script in W1.3.
- **Staging runs with `NODE_ENV=production`** so it behaves like production (secure cookies, no OpenAPI, required secrets). W1.2's demo mode switches staging's outside services to their test stand-ins.
- **The API's `onrender.com` address is public**, because Render runs health checks only on web services. It serves the same signed-in API the web app proxies; nothing links to it. Region is Ohio, the closest Render region to Texas with Virginia.
- **`render.yaml` is checked against Render's published JSON schema in CI**, when the schema can be downloaded; the Render CLI's validator needs an account.
