# Outside review — October 9, 2026

An independent read of the whole repository at `e86b522`, written for Justin. It covers what was verified, the bugs found, what the demo looks like to a stranger, where the product sits in the market, and a recommended order of work. Everything in the "Confirmed bugs" sections was checked by reading the actual code path; line numbers are from this commit.

## Verdict in five sentences

The engineering is far better than a six-day, agent-built, 96,000-line codebase has any right to be: tenant isolation is enforced by the schema, money paths use integer cents and real database invariants, filings are immutable and idempotent, and the offline phone model is sound. The product has never been touched by a real septic company or a real phone, and that, not code quality, is now the whole risk. The compliance differentiator the product is built on is already sold by a Texas competitor, Fieldbase On-Site, at roughly a third of the per-contract price, so "we know the county rules" is table stakes, not a moat. Three real bugs need fixing before any pilot: a Stripe Billing path that can bill a company twice, a second-phone path that strands a technician's whole inspection, and the fictional Example County being selectable by real companies. The right next move is to stop adding features, fix those, get continuous integration running again, and put the app in front of five providers.

## Confirmed bugs, ranked

### P1. Stripe Billing can charge a company a partial amount now and the full amount again a day later

`packages/billing/src/stripe.ts:32-67` creates the monthly Aerowise invoice with `auto_advance: true`, adds each line as a separate call, then finalizes. The local `billing_periods` row is written only after all of that, in `packages/billing/src/run.ts:100-114`. If the worker restarts between creating the draft and adding the last line (a deploy, a crash), Stripe auto-finalizes the partial draft about an hour later and charges the card. The local period is still `pending`, so every later run replays the same idempotency keys, hits "invoice is no longer editable", and fails. After Stripe's 24-hour idempotency window expires, the next run creates a brand-new full invoice. Net effect: the company pays the partial amount plus the full amount, and the first charge is never recorded locally because the webhook for an unknown invoice id is consumed and ignored (`run.ts:177-186`).

Fix: create the invoice with `auto_advance: false`, store `providerInvoiceId` immediately after the draft is created, add lines, then finalize with `auto_advance: true`. Do not record a billing webhook event as handled when the period is not found.

### P1. A technician who restarts an inspection on a second phone loses the whole inspection

`apps/web/app/tech/page.tsx:145-167` mints a fresh client id whenever the phone has no local draft for a job. The route payload (`packages/domain/src/jobs.ts:60-100`) never tells the phone that an inspection already exists for that job, so a job that is `in_progress` on the server shows as "To do" with "Arrive and start inspection". When the second inspection syncs, `apps/api/src/routes/inspections.ts:432` answers 409 `job_has_inspection`, every photo then gets 404, and "Try again" fails forever. Nothing on the server can adopt or re-key it.

How a tech hits this: phone dies mid-route and they borrow the office spare; a shared phone where another sign-in tidied the draft away (`apps/web/lib/offline/tenant.ts:58-59`); iOS evicting IndexedDB after a week of non-use. Fix: include the existing inspection's client id and status in the route stop so the phone adopts it, or let the server attach a new client id to an existing in-progress inspection.

### P1 on staging, P2 in production. A real company can file under the fictional Example County

`apps/api/src/routes/filings.ts:195-197` accepts any active jurisdiction when assigning a site's authority, and `GET /jurisdictions` lists the fictional one to every organization. The fictional ruleset is loaded whenever the process is not production or is in demo mode (`apps/api/src/app.ts:179`), and nothing ever deactivates it. On staging, where trials and prospect companies share the database with the demo, a real company's office user can pick "Example County Environmental Health (fictional)", get a 14-day made-up deadline, and have the filing auto-emailed to `filings@tx-example-county.example` through whatever mail provider is live.

Fix: refuse fictional jurisdictions for non-demo organizations in that route and filter them out of the list.

### P2. Homeowner can be charged twice through a stale Checkout page

Recording a manual payment (`apps/api/src/routes/invoices.ts:546-607`) never expires open Stripe Checkout sessions; only void does (`:505-520`). A homeowner who opened the pay page, left the tab, and then paid by check can still complete the Stripe page and be charged a second time. The money is tracked as overpaid, but the customer was actually charged twice and the office has to refund by hand.

### P2. Ordinary refunds call Stripe inside the transaction with a counter-based key

`apps/api/src/routes/invoices.ts:626-690` refunds through Stripe while holding the invoice lock and inserts the local row afterwards, with a key based on how many refunds exist locally. A lost commit means the next retry uses a new key and refunds again. The deposit path already does this correctly (reserve a row with a stored key, commit, then push); the ordinary refund route should use the same helpers.

### P2. Support-impersonation cookie survives platform-admin logout

`POST /admin/auth/logout` (`apps/api/src/routes/admin.ts:158-170`) revokes the admin session but not the separate one-hour `aw_support_session` cookie that grants owner-level read access to a company, including the full data export download. Sign out of admin on a shared machine and the next person still has that access for up to an hour.

### P2. Phone-supplied timestamps drive compliance deadlines with no bounds

`completedAt` from the phone is validated only as an ISO string (`packages/domain/src/inspections.ts:346`) and then drives the ruleset version, filing deadline, next-due date and late-fee logic (`packages/compliance/src/filings.ts:347, 280-297, 191-202`). A phone with a wrong clock opens every filing already late, or under a ruleset version that was not in force. Clamp to a window around server time and require `completedAt >= arrivedAt`.

### P2. Inspections synced for a job the office cancelled or reassigned are stranded

Work visits have a "held for review" path; inspections do not. `apps/api/src/routes/inspections.ts:366-370` answers hard errors for reassigned, cancelled or completed jobs, so a tech who finishes a stop offline after the office moved it has readings and photos the office can never see or accept.

### P2. Degraded network hangs the technician app on "Loading your route"

The service worker (`apps/web/public/sw.js:55-59`) and the startup fetches (`apps/web/app/tech/page.tsx:89-124`) have no timeouts; cached data is used only when a fetch rejects outright. One bar of LTE in a pasture keeps the socket open for 30 to 90 seconds before failing. Browser emulation never shows this because its offline mode fails instantly.

### P2. Task queue re-runs long tasks concurrently

`packages/tasks/src/queue.ts:41-56` reclaims any task locked more than 10 minutes ago and never extends the lock while running. A large export, a QuickBooks sync, or a report batch that takes longer gets picked up by a second worker and runs twice.

### P2. Migrations do full-table rewrites under exclusive locks at every boot

`packages/db/src/migrate.ts:12-43` runs each file in one transaction from API and worker start-up. `0060_service_cycles.sql:62-66` backfills and rebuilds constraints on `service_obligations`; `0016`, `0048`, `0059` do similar on contracts, jobs and systems. Fine at demo size; a liability at 2,500 contracts with rolling deploys. No checksum of applied files, no dirty-state marker.

### P2. Stripe Billing webhooks for unknown invoices are swallowed

Covered under the first P1: `run.ts:177-186` records the event id and returns 200 for an unknown invoice, so Stripe never retries. A dropped `payment_failed` means the company never goes past due. There is no reconciliation poll.

The remaining P3 items (platform fee not refunded on Connect refunds, row locks held across Stripe calls, int4 overflow on large lines, plaintext pay and renewal tokens, rate limiter keyed on the token being guessed, no MFA for platform admins, demo Twilio webhook forgeable from a constant in source, signature pad not scaled for device pixel ratio, service worker cache never pruned, no `pagehide` flush for the 400 ms debounce, GPS silently null on denial, ruleset versions can never be retired, UTC date used once in the authority report's complaint period, seed guard depends on `NODE_ENV`) are listed at the end.

## What a stranger sees in the demo

The demo works, provisions in about ten seconds, and the technician flow (route, stop card with gate code and directions, inspection form) is genuinely good on a phone. These are the things that would make a provider hesitate:

- **The office has 22 top-level navigation items** (`apps/web/app/(office)/layout.tsx:22`) in a flat row: Inbox, Schedule, Work, Estimates, Disposal, Due, Filings, Renewals, Invoices, Service items, QuickBooks, Texts, Customers, Sites, Plans, Trucks, Import, Users, Company, Billing, Subscription, Export. A four-person office does not want to choose between Due, Schedule, Work and Filings every time. Group into roughly five: Today, Work, Customers, Money, Settings.
- **Every demo site reports to "Example County Environmental Health (fictional)".** The marketing page lists 21 real authorities, but the product's one differentiator is invisible in the demo. A Hays County provider cannot see what Hays filing looks like.
- **Completed visits with no history.** The seed marks past visits "completed" (`packages/db/src/seed.ts:304-306`) without creating inspections, so a site shows visits #1 and #2 completed above a compliance history that says "Nothing recorded yet". A prospect will notice.
- **The marketing page shows every county as "In progress".** All 21 rows. That honesty is correct, but it reads as "nothing works yet". Show the two or three you intend to pilot with, and what "in progress" means.
- **No screenshots, no logo, default-looking styling** on the marketing page. Fine for a pilot conversation you are in the room for; weak for anyone who finds it alone.
- **Pricing on the page is $1.50 per contract plus a $99 minimum.** See market below; this is three times the incumbent.
- **The inspection form should be reviewed by a licensed maintenance provider.** It is a reasonable form, but field names like "Sludge in pump tank" versus the demo's own "sludge near the top of the pretreatment tank" suggest nobody who does this work has read it.

## Where it sits in the market

From outside research with sources (full report available on request):

- **Fieldbase On-Site** (Dayton, TX) is the direct competitor: Texas aerobic maintenance providers, mobile inspections with GPS and photos, "1-click county filing", e-sign renewals with payment, dispatch. Solo $50/month up to 100 contracts; Teams $50 plus $0.50 per active contract. The repo's own service-workflow plan was written from Fieldbase's public page, so this is known, but the pricing gap is not addressed anywhere.
- **SepticCycle** is $149 flat with Texas county templates. SepticMind, Tank Track and ServiceCore are septic or liquid-waste generalists without Texas filing. Jobber and Housecall Pro are the generalists providers actually use today.
- **Filing is three different integration types, not one.** Email PDF (Brazoria, Kaufman, Montgomery, Harris contracts), MyGovernmentOnline uploads (Williamson, Travis, Ellis, Grayson), and county-specific structured portals that want fields, not a PDF (Fort Bend's portal with a published 27-column CSV schema, Collin's own portal, SJRA's form). The product's CSV export framework is the right idea; the first real adapter should be Fort Bend's published schema because it is documented.
- **Regulatory facts the product must honor** (30 TAC 285.7): report to the permitting authority at least every four months and within 14 days of the test; two tests a year suffice for systems with electronic monitoring and remote access; 30-day written notice to the authority, manufacturer and owner before service ceases; TCEQ licenses individuals, not companies, so the contract is with a person; HB 1237 (effective September 2025) lets an expired license keep working for 90 days after renewal is submitted, so do not hard-block techs on expiry; TCEQ's Chapter 285 rewrite explicitly lists maintenance-contract requirements as in scope, with no proposal published yet.
- **Market size is small.** About 1,369 licensed maintenance providers and 1,199 technicians in Texas, probably well under a thousand companies, and a few hundred in the 200 to 2,500 contract band. At $1.50 per contract the Texas ceiling is low single-digit millions of annual revenue at full share. That is a fine niche business; it is not a venture story unless it expands to pumping-heavy work or other states.
- **$1.50 per contract per month is roughly 4 to 9 percent of a $200 to $500 annual homeowner contract.** Fieldbase anchors the market at $6 per contract per year plus $50. Consider $0.50 to $0.75 per contract with a base fee, or charge for filing adapters and the homeowner portal instead of per contract.

The things that decide whether this becomes a business are all outside the repo: a provider who will use it alongside their current process, a county whose filing you can prove, and a price that beats the incumbent or a reason to pay more. The recommended posture for the next month is: fix the three P1s, revive CI, cut the demo down to one believable county story, and spend the rest of the time on the phone with providers. ## P3 findings, for the backlog

Security and operations:
- Refunds on Stripe Connect direct charges do not pass `refund_application_fee`, so the company's balance is short the platform fee on every refund (`packages/payments/src/stripe.ts:83-88`).
- Row locks held across Stripe HTTP calls in `lib/checkout.ts:74-118` and `routes/invoices.ts:630-660`.
- Invoice line amounts can overflow int4 and surface as a 500 (`packages/domain/src/invoices.ts:139-152`).
- Pay-link and renewal tokens stored in plaintext with no expiry (`lib/invoices.ts:210`, `packages/renewals/src/renewals.ts:15`); other tokens are hashed.
- Public-token rate limiters keyed on the token being guessed (`routes/users.ts:33`, `password-reset.ts:22`); file routes have none.
- Platform admins have password-only login, no MFA, and can erase any organization.
- On the hosted demo, the SMS webhook is verifiable with a constant from source (`packages/sms/src/test-provider.ts:4`); demo-only impact.
- Dashboard-made Stripe refunds default to `intent = credit`, which may not match what the office meant.
- QuickBooks totals are only compared after create when tax mode is on (`packages/quickbooks/src/sync.ts:547`).
- Billing counts contracts "on the 1st" whenever the first run of the month happens.

Phone:
- Signature pad is sized once in CSS pixels with no device pixel ratio scaling (`components/forms/SignaturePad.tsx:17`).
- Service worker caches every hashed chunk forever and never prunes (`public/sw.js:7, 66-75`).
- 400 ms debounce with no `pagehide` or `visibilitychange` flush; a photo lives only in memory for up to 3.5 seconds before the IndexedDB write.
- GPS silently null on permission denial, with no indication to the tech or the office.
- Inspection sync carries no revision number; work sync does.
- A held-then-dismissed work record locks that visit on the phone forever.
- Photo orientation relies on browser EXIF defaults in `createImageBitmap`; needs a real device check.
- An unexpected error inside a sync pass leaves the banner on "Sending N changes" with no retry button until the 20-second timer.

Data and domain:
- Ruleset versions can never be retired or given an `effective_to`; a bad published version has no kill switch.
- `sent` and `confirmed` filings are not tied to a submission package at the database level.
- `packages/compliance/src/reports.ts:129-140` uses a UTC date to pick the contract for the complaint-response period.
- Cancelling a contract leaves an in-progress job whose completion cannot complete the visit.
- Renewal start is pinned to the old end date regardless of activation date.
- `background_tasks` is never pruned and the filing lookup filters on an unindexed JSON field.
- Audit log has no before/after image and no time-ordered index.
- Seed and reseed guards depend on `NODE_ENV` being set rather than the database name.
- Date engine quirk: a term starting Feb 29 ends one day short and shifts the renewal chain permanently.

## Fort Bend bulk-upload schema

[Field-by-field specification](../jurisdictions/research/fort-bend-bulk-upload-2026-10-09.md), from the county's own April 2025 instructions and August 2025 portal guide (PDFs hashed in the document). Twenty-seven comma-separated columns: date, inspection type (four literals), service company (must match the county's own name list), technician, twelve component flags as `Operational`/`Inoperative`, `Needs Pumping` as `Yes`/`No`, four lab values each with a free-text test method, comments, and the permit number which must match exactly. Blank fields still take their commas. No PDF is uploaded; the county goes by the fields. Contracts go up one PDF at a time with a $50 fee per contract year.

What building the adapter needs beyond the existing ruleset export framework: a value-mapping step (pass/fail to Operational/Inoperative, boolean to Yes/No), a mapping from the inspection template's fields to the county's twelve components (several, such as Recirculation Pumps and Sprayfield Vegetation, have no field today), and answers to the document's unknowns list: header row or not, quoting of commas in comments, date format confirmation, and the exact service-company string. One call to 281-342-7469 or a test account on the portal settles those. The repo's own gate (only the fictional authority may carry an export block until the authority's format is confirmed) is the right rule to keep.
